# How to configure the client

To change the client configuration, such as the URL base path, or the number of threads, or the total number of mesages to be uploaded,
Go to `ClientConfig.java` under `skiclient` folder. 

`SERVER_BASE_PATH_EC2` is for updating the remote EC2 server base path. 

`SERVER_BASE_PATH_LOCALHOST` is for testing of the server running on tomcat on local host. 

`NUMBER_OF_THREADS` is the total number of threads used for sending `POST` request to the server. 

`TOTAL_NUMBER_OF_POST` is the total number of messages randomly generated which is used by the client to send `POST` request to server. 

# How to run the client

To run the client, open the project in Intellij and go to `Main.java` file, then execute the main function in `Main.java`.

# Client design (part 1)

I designed the client on top of the swagger clients generated by the swagger website. 

I created a `ClientConfig` class to store the constant variables I used to implement the client project, such as the number of threads, server URL base path, 
and the number of random ski lifts generated. 

I developed a `EventGenerator` class which implements `Runnable` interface of java to act as the thread to generate random lift events. 
The events are then stored in a `BlockingQueue`. The `BlockingQueue` object is passed into this class
as a constructor parameter from the `Main` class `main` function because it is shared in `main` function between
the `EventGenerator` and `RecordUploader`. 

I created a `RecordUploadClient` class which takes a `SkiApi` class object. The `SkiApi` class is generated by swagger. 
`RecordUploadClient` use this `SkiApi` client and its function `writeNewLiftRideWithHttpInfo` to send post request to server. 
I also included other logic such as calculating the latency of the request and checking HTTP response code in `RecordUploadClient` class. 
The retry process for the `POST` request in case of not `201` response code is also implemented in `RecordUploadClient` class with a recursion call 
which calculates the number of retries in its parameter. Total number of retry is hard coded as 5 according to the assignment requirement. 
The `uploadLift` function will return `1` if the lift event is successfully uploaded (`201` response is received within 5 retries), or `0` if the lift event is not uploaded successfully (no `201` response is received during 5 retries).  

I implemented a `RecordUploader` class which implements `Runnable` interface of java to act as the upload thread for the lift events. It takes 4 arguments:
`RecordUploadClient`, `BlockingQueue`, `int limit` and another `BlockingQueue`. The `RecordUploadClient` is used to send post to the server with up to 5 retries per request. 
The first `BlockingQueue` stores the random lift rides generated by `EventGenerator`. `int limit` specifies how many requests will be uploaded by this thread until it ends. 
Passing `-1` for limit specifies the `RecordUploader` to keep send request until the input queue is empty. We have also passed in `1000` from `main` function
since the assignment requires to create 32 threads and upload 1000 request each. 
The second `BlockingQueue` is used to store the result returned by `RecordUploadClient.uploadLift` function. This result is later used in `Main` class `main` function to calculate the number 
of success and fail in sending requests to server. 

I implemented a `UploadEvent` to model the random lift events generated by `EventGenerator` and each randomly generated lift event is stored as a new `UploadEvent` object into the 
`BlockingQueue`. 

Finally I have the `Main` class which creates 2 `BlockingQueue`, one for generating events from `EventGenerator` thread, and one for storing the output from `RecordUploader` threads. 
Those 2 `BlockingQueue` objects are passed to `EventGenerator` and `RecordUploader` as input parameters. 
I used `BlockingQueue` because it's thread safe since we are going to use different thread to generate and upload the lift events, and multiple `RecordUploader` threads are created for calling the server. 
In main function, I took the current time before and after the upload process to calculate the total run time of the program. And I used the outputs stored in output `BlockingQueue` of `RecordUploader` to calculate
the number of success and failure in requests. Finally I calculated the throughput by dividing the total number of success requests with the total run time. 
For each `RecordUploader` thread, I created a new object of `RecordUploadClient` to make sure different threads do not impact each other when calling the server.  

# Client design (part 2)

The design of client part 2 is the same as part 1. But additionally, to satisfy the assignment requirement, I created a new class `LatencyRecord.java` to store the `(requestStartTime, requestType, latency, responseCode)` which is required to be stored for part 2. 
Every time a request is sent to the server, I created a new object of `LatencyRecord` and store it in another `BlockingQueue` which is passed to `RecordUploadClient` by `RecordUploadClient.setLatencyRecordQueue` function. 
Again I used `BlockingQueue` since it's thread safe. Multiple threads of the `RecordUploader` is writing to this queue through `RecordUploadClient` when sending requests to server. 

After all the requests are sent to the server, I created a file named `Part2RecordFile.csv` in `Main` and write the records from the `Blocking` queue to this file through java's `File` and `PrintWriter` class. 

I extracted all the latency field from the `LatencyRecord` in the `BlockingQueue` into a `List` and sorted them with Java's built-in `Collections.sort` function. 

I calculated the mean by dividing the sum of the latency with the total number of latency. 

I calculated the median of the latency by taking the latency at the middle number of the sorted latency `List` (`latencies.get(latencies.size() / 2)`.

I calculated the P99 by taking the 99th largest value from the latency `List` since it is sorted. 

I calculated the throughput by dividing the total number of requests with the total runtime. Total run time is calculated by end time minus start time of uploading lift events in main function. 

I calculated the minimum and maximum by taking the first and last latency in the latency `List` since the list is already sorted.

The output csv file is stored in `Part2RecordFile.csv` file of the client part 2 project.

## Little's Law throughput prediction

According to the code in client part2, mean response time of the requests for my client is `0.018` second. I used 32 client threads. 

So using Little's Law, my expected throughput should be `32/0.018` = 1778 requests per second. 

My actual throughput for client part 1 is 1694, which is within __5%__ difference of the expected throughput. 

My actual throughput for client part 2 is 1652, which is within 7% difference of the expected throughput.

However, my client part 1 runs with a throughput of 1694, my client part 2 runs with a throughput of 1652, the difference between part1 and part2 is within __5%__.
